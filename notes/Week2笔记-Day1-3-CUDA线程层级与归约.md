## 〇、CUDA 编程模型总览(把 Week1 Day6 的地基夯实)

**是什么**:CUDA = "用 C++ 写、在 NVIDIA GPU 上跑"的平台。核心思想是把 GPU 当**协处理器**:
- **host** = CPU + 主机内存(RAM),跑你的 `main()`
- **device** = GPU + 显存(VRAM),跑 kernel

两个世界各有各的内存,CPU **不能直接解引用** GPU 指针,反之亦然。数据要过 PCIe 桥搬运:

```
   host 世界                        device 世界
┌──────────────────┐   PCIe ~11.5GB/s   ┌──────────────────┐
│ CPU · RAM        │ ═════════════════▶ │ GPU · VRAM 24GB  │
│ main()           │   cudaMemcpy H2D   │ kernel(百万线程) │
│                  │ ◀═════════════════ │                  │
└──────────────────┘   cudaMemcpy D2H   └──────────────────┘
```

**有什么用**:AI Infra 的一切底层(vLLM 的 attention kernel、训练框架的算子)都是这套模型。

**怎么用**:固定 6 步骨架(Week1 Day6 的 `vector_add.cu` 已跑通,此后每个程序都是这个形状):

```
① cudaMalloc        在 GPU 上开辟显存
② cudaMemcpy H2D    把输入数据从 RAM 搬到 VRAM
③ kernel<<<...>>>   启动 kernel,GPU 上百万线程并行计算
④ cudaMemcpy D2H    把结果搬回 RAM
⑤ cudaDeviceSynchronize  等 GPU 干完
⑥ cudaFree          释放显存
```

### 常用 CUDA API 速查

| 函数 | 作用 | 类比 C++ | 易错点 |
|---|---|---|---|
| `cudaMalloc(void** p, size_t n)` | 显存上分配 | `new` | 传的是**指针的地址**(二级指针);分配完不会清零 |
| `cudaMemcpy(dst, src, n, dir)` | host↔device 拷贝 | `memcpy` + 搬运方向 | `dir` 四选一:`cudaMemcpyHostToDevice`(H2D)/`DeviceToHost`(D2H)/`DeviceToDevice`/`HostToHost` |
| `cudaMemset(p, 0, n)` | 显存清零 | `memset` | 累加器(+= 型 kernel 的输出)**必须**先清零,见 Day7 的 508=2×254 惨案 |
| `cudaFree(p)` | 释放显存 | `delete` | 忘了调 = 显存泄漏,长跑服务会 OOM |
| `cudaDeviceSynchronize()` | 阻塞等 GPU 全部完成 | (无) | kernel 启动是**异步**的,不等它就去读结果 = 读到垃圾 |
| `cudaGetLastError()` | 查最近一次 CUDA 调用/启动是否出错 | `errno` | **launch 参数非法(如线程>1024)不会崩**,只在这里冒头——不查就无声失败(Day7 实验 3 亲历) |
| `cudaEvent_t` 系列 | GPU 侧精确计时 | 秒表 | 见 §3.3 |

### 三种函数限定符

| 限定符 | 在哪跑 | 谁能调 |
|---|---|---|
| `__global__` | GPU | CPU 用 `<<<>>>` 启动(**kernel 的标志**) |
| `__device__` | GPU | 只能被 GPU 上的函数调(工具函数) |
| `__host__` | CPU | 普通 C++ 函数(不写就是它) |

## 一、线程层级:grid → block → warp → thread ⭐⭐(全 CUDA 最核心的心智模型)

**是什么**:启动一个 kernel 不是启动 1 个线程,而是启动**一支军队**。层级从大到小:

```
grid(一次 kernel 启动的全部线程)
 │
 ├─ block 0      ── 被调度到某个 SM(流式多处理器,GPU 的"核心")
 ├─ block 1      ── 可能调度到任何 SM,先后顺序不可控
 ├─ block 2
 └─ ...4096 个
      │
      ├─ warp 0  ── 真正的执行单位:32 个线程锁步,同一条指令
      ├─ warp 1      │  block 内按 threadIdx.x 每 32 个切一刀
      ├─ ...         │
      └─ warp 7      ▼
           thread 0..255(threadIdx.x)
```

四级各有一个内建变量(都是 `dim3` 类型,这里只用 `.x`):

| 内建变量 | 含义 | print_ids 例子里的值 |
|---|---|---|
| `threadIdx.x` | 线程在**本 block 内**的编号 | 0 ~ 7 |
| `blockDim.x` | 每个 block 有多少线程(你启动时指定的) | 8 |
| `blockIdx.x` | 本 block 在 grid 里的编号 | 0 ~ 3 |
| `gridDim.x` | grid 里有多少 block | 4 |

**有什么用**:每个线程靠这几个变量算出"我是谁、我该处理哪个数据"——**全局索引公式**(背下来,之后每个 kernel 第一行都是它):

```cuda
int i = blockIdx.x * blockDim.x + threadIdx.x;
//    ─────────┬─────────   ─────┬──────
//      "前面有几个整 block"   "我在本 block 内排第几"
```

**怎么用(具体数字举例)**:4 block × 8 thread,block 2 里的 thread 5:
```
i = 2 × 8 + 5 = 21
```
就像电影院排座位:**第 2 排的第 5 个座位 = 前面 2 整排 × 每排 8 人 + 第 5 个**。这样 32 个线程算出 0~31,一人一个数,不重不漏(当时实测验证过)。

**为什么要有 block 这一层(而不是一大坨平铺的线程)?**
- block 是 **SM 的调度单位**:一个 block 整体住进一个 SM,住完才让位。GPU 快是因为 82 个 SM 同时招待大量 block。
- **block 内**可以通信(共享 `__shared__` 内存、`__syncthreads()` 同步);**block 之间不能**(它们可能不同时刻在不同 SM 上)——这是 Day3 归约树只能做到 block 内的根本原因。
- 一个 block **最多 1024 线程**(硬件上限,Day7 实验 3 撞过:2048 直接启动失败)。

**warp 是什么(32 个线程的"连体婴")**:硬件真正发射指令的最小单位。同一个 warp 的 32 个线程**永远执行同一条指令**,只是操作各自的数据(SIMT)。推论:
- 你写的是 256 线程的代码,硬件按 8 个 warp 分组执行;
- 若 warp 内线程走了不同分支(如奇偶走不同 if),硬件只能**先执行一支、再执行另一支**(warp divergence),白白损失并行度——Day5 结尾提的"分支发散"伏笔在此;
- 后续优化(coalescing、bank conflict、tensor core)全部以 warp 为分析单位,Day7 Q5 专门讲。

**坑**:
- **不能假设线程执行顺序**。实测 `print_ids` 输出乱序:block 2 的输出可能比 block 0 先出现——block 跨 SM 的调度顺序不可控。**任何依赖"block 0 先算完"的代码都是错的**,需要顺序就上同步原语。
- `printf` 在 kernel 里能用,但输出要等 `cudaDeviceSynchronize()` 之后才冲得出来(异步)。
- ⚠️ **仓库里 `print_ids.cu` 的注释与代码不一致**:`print_ids<<<4, 10>>>();` 实际是每 block **10** 线程(注释和 cout 都写的 8)。跑这份源码会看到 40 个线程、i 最大到 3×10+9=39。公式不变,但读代码时**以启动参数为准、别信注释**——这本身就是个真实教训(代码会改,注释会忘改)。

## 二、Day3 主角:并行归约(Reduction)

**是什么**:把 N 个数**归并**成一个数(这里是求和 `Σx[i]`)。串行要 N-1 步;并行的经典做法是**树状归约**:两两配对、逐层减半,`log₂N` 层完成。

```
串行(1 个算 N-1 次):            并行归约树(每层所有对同时算):
s = x0+x1+x2+...+x7              x0  x1  x2  x3  x4  x5  x6  x7
一个接一个加                       \  /    \  /    \  /    \  /
                                   x0+x1  x2+x3  x4+x5  x6+x7      ← 4 个加法同时发生
                                     \    /        \    /
                                     前两对之和    后两对之和        ← 2 个同时
                                        \          /
                                          最终总和                ← 1 个
```

**有什么用**:归约是仅次于 matmul 的第二大 kernel 家族——loss 计算、softmax 分母、attention 的 sum/max、梯度平均(分布式 allreduce 的底层)全是它。

**怎么算一个具体的数(8 元素手推,后面代码对照)**:数组 `[1,2,3,4,5,6,7,8]`,8 个线程各持一个数进 shared 数组 `s[]`:

| 轮次 | stride | 干活的线程 | 动作 | s[] 变成 |
|---|---|---|---|---|
| 1 | 4 | tid 0~3 | `s[0]+=s[4]`, `s[1]+=s[5]`, `s[2]+=s[6]`, `s[3]+=s[7]` | `[6, 8, 10, 12, ·, ·, ·, ·]` |
| 2 | 2 | tid 0~1 | `s[0]+=s[2]`, `s[1]+=s[3]` | `[16, 20, ·, ·, ...]` |
| 3 | 1 | tid 0 | `s[0]+=s[1]` | `[36]` = 1+2+…+8 ✔ |

关键观察:**每层只有前 stride 个线程干活,其余在屏障处等待**;3 层 = log₂8。真实代码 blockDim=256,即 8 轮(stride 128→64→…→1)。

## 三、版本 A:`reduce_atomic.cu`(逐行精读)

### 3.1 完整逻辑

```cuda
__global__ void reduce_atomic(const float* x, float* sum, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // 老朋友:全局索引
    if (i < n) {
        atomicAdd(sum, x[i]);      // 每个线程:把 x[i] 原子地加到 *sum 上
    }
}
```

100 万个线程,每人只干一件事:**把自己的数加到同一个 `sum` 上**。没有树、没有层次——最暴力的并行。

### 3.2 变量字典

| 变量/表达式 | 是什么 | 值/含义 |
|---|---|---|
| `N = 1 << 20` | 数据量,位移写法 2²⁰ | 1,048,576(100 万)个 float |
| `h_x` | host 侧 vector,RAM 里 | 全填 `1.0f` → 正确和必然 = N |
| `d_x` / `d_sum` | device 指针,VRAM 里 | cudaMalloc 分配;d_ 前缀是惯用法 |
| `threadsPerBlock` | 每 block 线程数 | 256(经典值:是 32 的倍数 → warp 不浪费) |
| `numBlocks` | block 数,**向上取整公式** | (2²⁰ + 255)/256 = **4096** |
| `sum` 指向的 4 字节 | 全部线程抢着加的**唯一目的地** | 串行化热点,见 3.4 |

两个 main 细节:
- **`cudaMemset(d_sum, 0, sizeof(float))`**——累加器先清零。`atomicAdd` 是往旧值上加,旧值是垃圾则结果必错。(Day7 实验 1 的 508.276 = 2×254.138 就是忘了这步:kernel 跑了两遍、各加一次。)
- **测试数据全 1.0f 不是偷懒**:浮点加法**不满足结合律**,百万线程累加顺序随机,一般数据下 GPU/CPU 会有可感知的微小舍入差;全 1 时任何顺序加出来都精确 = N,校验干净。选测试数据也是一种设计。

### 3.3 `atomicAdd` 与计时,两个"为什么"

**为什么需要 atomic(竞争条件实例)**:`sum += x[i]` 在机器层面是三步:**读 → 加 → 写**。两个线程不加保护地同时做:

```
时刻   线程 A                     线程 B                *sum 的值
t1     读 *sum ──────────▶ 5
t2                                读 *sum ──────────▶ 5   (A 还没写回!)
t3     加:5+3=8
t4                                加:5+7=12
t5     写回 8 ──────────▶ 8
t6                                写回 12 ──────────▶ 12   (A 的 3 丢了!)
正确答案 5+3+7=15,实际得到 12 —— 一次更新被覆盖
```

`atomicAdd(sum, x[i])` 把三步焊成一个**不可分割**的硬件原语(在 L2 cache 上由硬件仲裁),同一时刻只放一个线程进去做——**正确但排队**。

**为什么用 cudaEvent 计时而不用 CPU 的 clock()**:kernel 启动是异步的,CPU 秒表测的是"含等待的墙钟";`cudaEvent` 是**在 GPU 流里打的时间戳**,测的纯是 GPU 侧 kernel 时长,还自动排除了 H2D 拷贝(拷贝在 start 事件之前就完成了)。

```cuda
cudaEventRecord(start);            // 流里插一个"开始"戳
reduce_atomic<<<4096, 256>>>(...); // kernel 入队
cudaEventRecord(stop);             // 流里插"结束"戳(排在 kernel 后)
cudaEventSynchronize(stop);        // CPU 等到结束戳被执行
cudaEventElapsedTime(&ms, start, stop);  // 两个 GPU 时间戳之差
```

### 3.4 实测与算账:18 ms 都花在哪了

**账本一(原子串行化)**:100 万个线程挤**同一个地址**,原子操作再快也是排队的——18 ms / 100 万次 ≈ **每次 18 ns**。这版 kernel 的耗时主体就是这 100 万次排队,不是计算也不是读数据。

**账本二(理论地板)**:这 kernel 必要的访存 = 读一遍 4 MiB:
```
有效带宽 = 4,194,304 B ÷ 18 ms ≈ 0.23 GB/s   ← 3090 峰值 936 GB/s 的 0.02%!
理论地板 = 4 MiB ÷ 936 GB/s ≈ 4.5 µs          ← 实测 18 ms 是它的 4000 倍
```
说明:**绝对耗时被原子串行 + 环境噪声支配,离任何硬件极限都极远**。这正是要写版本 B 的动机——把 100 万次全局原子干掉。

**坑**:
- `atomicAdd` 支持类型有限(int/float/unsigned 等整型浮点;`double` 要 sm_60+ 才有,复数/自定义类型没有——那种要靠"每线程私有结果 + 分块归并"绕开);
- 原子操作解决**正确性**,天然牺牲**性能**——它是"让程序对"的工具,不是"让程序快"的工具;
- 忘 `cudaMemset(d_sum, 0, ...)` → 结果是垃圾值 + N。

## 四、版本 B:`reduce_shared.cu`(优化:块内先归约,原子只留 4096 次)

### 4.1 优化思路(优化了什么、怎么优化的)

版本 A 的病根:100 万线程 × 全局原子 = 100 万次跨 SM 排队。
药方分两级:

1. **块内**用 `__shared__` 内存 + 归约树:256 个数归并成 1 个(8 轮,全在片上,无原子);
2. **块间**只剩 4096 个"块结果"需要合并 → 原子操作从 **100 万次降到 4096 次**(降 256 倍,占比变得可忽略)。

```
版本A:  1M 线程 ──────全部 atomicAdd──────▶ 1 个 sum     (100 万次排队)

版本B:  1M 线程 ─▶ 每 block 256 人先树状归并 ─▶ 4096 个块结果 ──atomicAdd──▶ 1 个 sum
                        (片上 shared,零原子)              (只剩 4096 次排队)
```

### 4.2 逐行精读

```cuda
__global__ void reduce_shared(const float* x, float* sum, int n) {
    __shared__ float s[256];        // ① 片上快内存,本 block 独享

    int tid = threadIdx.x;           // block 内编号 0..255
    int i   = blockIdx.x * blockDim.x + threadIdx.x;  // 全局编号

    s[tid] = (i < n) ? x[i] : 0.0f; // ② 各自把数据从 global 搬进 shared
    __syncthreads();                // ③ 等全 block 搬完才能开始归并

    for (int stride = blockDim.x/2; stride > 0; stride >>= 1) {
        if (tid < stride) {
            s[tid] += s[tid + stride];   // ④ 两两配对,逐层减半
        }
        __syncthreads();            // ⑤ 每层结束都要屏障!
    }
    if (tid == 0) {
        atomicAdd(sum, s[0]);       // ⑥ 每 block 只由 0 号线程交一次卷子
    }
}
```

| 行 | 知识点 |
|---|---|
| ① | `__shared__`:block 级私有片上内存。生命周期 = block 存在的期间,block 结束即消失。延迟几十 ns(vs global 几百 ns),是 block 内线程**唯一**的共享通信渠道 |
| ② | 边界保护:N 不整除 256 时,越界线程填 0(加 0 不影响和)——本例 N=2²⁰ 恰好整除,保护不触发,但通用写法必须带 |
| ③⑤ | `__syncthreads()`:block 内**屏障**,全 block 256 人都到达才放行。③ 防"有人还没写入 s 就被别人读";⑤ 防"下一层读到上一层没算完的值"——**每层归并后都要一道,少一道就错** |
| ④ | stride 从 `blockDim.x/2` 开始(=128),每轮 `>>= 1` 右移减半(128→64→…→1),共 log₂256 = 8 轮 |
| ⑥ | `if (tid == 0)`:一个 block 只许一个人写全局,否则又退化成 256 次竞争 |

**一处容易忽略的正确性细节**:`__syncthreads()` 写在 `if (tid < stride)` **外面**。CUDA 规定 block 内**所有**线程都必须到达屏障——若把 sync 放进 if 里,后半线程永远到不了屏障 → **死锁/未定义行为**。"干活的线程少,等着的线程一个都不能少。"

### 4.3 实测:15.75 ms,只比 18 ms 快约 13%——复盘

```
加速比 = 18 ÷ 15.75 ≈ 1.14×(提升 12.5%)
```

**为什么才 13%?**(当时的关键一课,直接通向 Day6)

- 消掉的 100 万次原子(账本一)本就**不是唯一大头**:这 kernel 属于典型的**小任务 + 短命 kernel**,启动开销、低时钟、共享宿主噪声在两个版本里都全额存在,优化动不了它们;
- 剩下的必要成本里,**读 4 MiB 输入是省不掉的**——这是"干这活至少要付的钱";
- 用 Day6 的 Roofline 语言复盘:归约的**算术强度**
  ```
  AI = FLOP ÷ 字节 ≈ (N−1) 次 加法 ÷ N×4 B = 0.25 FLOP/B
  ```
  0.25 远低于 3090 平衡点 38 FLOP/B → **天生 memory-bound**,算力永远不缺,优化只能在"少搬/搬快/少同步"上做文章。巧的是 0.25 正好等于 Day6 算出的 naive matmul 的 AI——两个 kernel 撞的是同一堵墙。

**还剩哪些瓶颈(后续可做的优化,现在只需知道方向)**:
1. **每层只有一半线程干活**:stride=1 那轮 256 人里 1 人干活 255 人看——最后几轮(warp 内即可完成的部分)可用 `__shfl_down_sync` 寄存器直接交换,免 shared 免屏障;
2. **一个 block 只读 1 KB 就退出**:可用 **grid-stride loop** 让少量 block 循环多读几段(减少启动/退出的摊销);
3. **向量化装载**:一次读 `float4`(16 B),装载指令砍 4 倍——正是 Day7 梯子里 kernel 6 的同一招;
4. N÷256 = 4096 个 block 各自独立归并的最后一步,可改成**两阶段 kernel**(第一个 kernel 写 4096 个部分和,第二个 kernel 归并它们)彻底避开原子。

> [!tip] 方法论沉淀
> 这 13% 是 Week2 第一次"**优化了正确的东西,收益却不大**"——教训:先判断瓶颈在哪(原子?访存?启动开销?),再动手;**盲优白费**。这个直觉在 Day6 得到工具化(nsys/ncu/Roofline),在 Day7 得到方法论化(优化梯子:一级只修一个主瓶颈)。

## 五、性能指标计算小抄(通用,后续每天都在用)

| 指标 | 公式 | 本篇实例 |
|---|---|---|
| 耗时 | `cudaEventElapsedTime`(GPU 侧时间戳) | 18 ms / 15.75 ms |
| 加速比 | t_旧 ÷ t_新 | 18 ÷ 15.75 ≈ 1.14× |
| 数据量 | 元素数 × sizeof | 2²⁰ × 4 B = 4 MiB |
| 有效带宽 | 数据量 ÷ 时间 | 4 MiB ÷ 18 ms ≈ 0.23 GB/s |
| FLOP 数(归约) | N − 1 次加法 | ≈ 1.05 MFLOP |
| 算术强度 AI | FLOP ÷ 搬运字节 | ≈ 0.25 FLOP/B(memory-bound) |
| 理论时间地板 | 必要搬运量 ÷ 峰值带宽 | 4 MiB ÷ 936 GB/s ≈ 4.5 µs |
| 利用率 | 实测吞吐 ÷ 硬件峰值 | (Day5 起:TFLOPS ÷ 35.6) |
| 波数 waves | 总 block 数 ÷ SM 数 | 4096 ÷ 82 ≈ 50 波(Day7 尺寸效应用它) |

**RTX 3090 关键参数(sm_86 / GA102)**:82 个 SM · FP32 峰值 35.6 TFLOPS · 显存带宽 936 GB/s · 每 block 上限 1024 线程 · warp=32 · shared/block 默认 48 KiB。两个"帽"——算力帽和带宽帽——孰先顶住,由 AI 与平衡点(≈38 FLOP/B)的对比决定。

## 六、坑合集(Day1-3)

1. **线程乱序是特性不是 bug**:block 调度顺序不可控,依赖顺序的逻辑必然出错。
2. **注释会骗人**:`print_ids.cu` 注释写 8 线程、代码是 `<<<4, 10>>>`;以启动参数为准。
3. **累加器必须清零**:`atomicAdd`/`+=` 型 kernel 的输出先 `cudaMemset` 0(Day7 508=2×254 惨案同源)。
4. **`__syncthreads()` 必须全 block 线程可达**:放进 if 里 = 死锁;且**每层**归并后都要,漏一道结果错。
5. **launch 错误不报错**:线程数超 1024 等参数错误不崩程序,只能靠 `cudaGetLastError()` 抓(Day7 实验 3:610 TFLOPS 的假数据就是这么来的)。
6. **小 kernel 绝对耗时含大量噪声**:理论地板 4.5 µs 的活实测 18 ms——绝对值只用来粗判数量级,结论靠相对对比 + 交叉验证。
7. **浮点加法无结合律**:并行归约顺序不定;测试数据用全 1 规避校验歧义。
8. block 间**没有**同步原语(没有 `__syncthreads` 的跨 block 版),跨 block 合并只能靠原子或再启一个 kernel。
