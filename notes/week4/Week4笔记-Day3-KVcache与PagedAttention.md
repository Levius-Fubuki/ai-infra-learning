## 〇、KV cache:是什么、为什么必须存在(时间换空间)

**是什么**:生成第 5 个 token 时,attention 要算 `Q₅·K₁..₅`。把历史每层的 K/V 存在显存里,每步只算**新 token** 的 K/V 投影。

**没有它会怎样**:
```
不缓存:生成第 t 步要把前缀 1..t 的 K/V 投影全部重算一遍
  生成 T 个 token → 重算量 ~ T(T+1)/2 次投影 + O(T²) attention → 平方级浪费
缓存后:每步只算 1 个新 token 的 K/V 投影 → 总共 T 次 → 线性
  代价:显存随已生成 token 数线性涨(56KB/token)
```

**代价曲线(Q2 完整版)**:显存 0→O(T) ↑,计算 O(T²)→O(T) ↓——这才叫"换"。KV cache 是"对"的做法(所有框架都做),**差距在怎么存**——PagedAttention 登场。

**GQA 复习**:Qwen2.5-7B 的 28 个 Q 头共享 4 组 K/V → 每 token KV = 2×28层×4头×128维×2B = **56KB**(精确 57,344B);若无 GQA(28 KV 头)则 ×7 = 392KB——GQA 是 KV 时代模型设计的标配。

## 一、PagedAttention:像 OS 虚拟内存一样管 KV ⭐

### 1.1 碎片之一:内部碎片(预留了没用)

传统做法:**每个请求按 max-model-len 预留一整块连续显存**。问题在于 LLM 生成长度不可预测,只能按最坏情况预留:

```
max-model-len=8192 → 每个请求预留 8192 × 56KB ≈ 458MB 连续块
  请求实际只生成 300 token → 用 300×56KB ≈ 17MB,剩下 441MB 是"预留了但没用"的空白

[请求A 预分配 458MB ██████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░]
                     └─ 300tok 用到这 └─ 浪费 7892 tok 的预留(内部碎片)

单请求内部碎片 = (max-len − 实际长度) × 56KB
  · 平均请求只生成几百 token 时,内部碎片往往占预留的 90%+
  · 它是"资源被请求独占却用不满"——内存利用率 60-80% 的头号来源
```

### 1.2 碎片之二:外部碎片(释放后凑不齐)

请求结束释放自己的块,但**块必须连续**才够下一个请求用:

```
时间线上,多个请求连续开/关:
  [A██][空闲][B██][空闲][C██]...
    A、C 结束释放后:
  [空闲][B██][空闲][空闲][D██]...
              └─ 空闲块分散成一小段一小段
新请求 E 需要 400MB 连续显存 → 总量够,但凑不出一整块 → E 被拒绝/等待

对比:内部碎片 = "一个请求内,预留 > 实际";外部碎片 = "请求间,洞凑不齐"
  根源都是"要求物理连续 + 按最坏情况预留"
```

### 1.3 分页怎么解(两个碎片一起消)

```
PagedAttention(block_size=16 token):
  每个请求维护一个"逻辑页表",逻辑页 [0][1][2]... 映射到任意物理块(像 OS page table)
  生成到哪一页才分配哪一页的物理块

消内部碎片:按需分配 → 短请求只占短
  300-token 请求 → ceil(300/16)=19 个块,不再预留 8192
  → 内部碎片从 (max-len−实际)×56KB 降到最多 15 tok(不满一块的尾部)
消外部碎片:物理块不必连续
  逻辑页 0,1,2 可能对应物理块 [17][3][92](任意位置)
  请求结束 → 它的块立刻回池 → 谁需要谁拿 → 没有"洞",只有"空闲块"
利用率 60-80% → 近 100%

对比传统:
  传统:逻辑连续 + 物理必须连续 → 两个碎片
  Paged:逻辑连续 + 物理随意(靠页表) → 两个碎片都消
  换出:池满时还可把某些请求的块 swap 到 CPU(pending),而不是直接失败
论文数据:吞吐 2-4× Orca(当时的 SOTA)、23× HF transformers
```

### 1.4 共享:引用计数让一份 KV 服务多个请求 ⭐

**前提**:所有请求对 KV 块**只读**——K/V 一旦算出,后续 attention 只是读它们,不修改。所以同一块可以安全地被多个请求同时指向。

**三种典型共享**:

```
① 前缀共享(system prompt):10 个请求用同一段 system prompt
   → 这段的 KV 只算一次,10 个请求的页表都指向同一批物理块
② 多轮对话:新一轮提问带历史 → 历史部分 KV 复用,只算新增部分
③ beam search / 并行采样:同一前缀发散 N 条路径 → 前缀块共享
```

**机制(像 OS 共享内存 + 引用计数)**:

```
每个物理块有个 ref_count:
  · 被 10 个请求引用 → ref=10
  · 某个请求结束/移出页表 → ref-- 
  · ref 归 0 → 才算真正空闲,可回收给新请求
  · 共享的块从不被写,只被读 → 无写冲突,安全

[物理块#5](ref=10):10 个请求的 system prompt KV
  → 省下 9 份重复的 KV 存储和计算
```

**面试关联**:Day3 面试答案里"③共享"为什么值钱——system prompt 越长、并发越高,前缀共享省得越多(长 system prompt 的 KV 只算一次)。这也是为什么长 prompt 应用对 PagedAttention 红利更大。

### 1.5 与 W3 Day6 的连接:同一"分块"思想两个投影

```
Flash-Attention(W3):分块 → S/P(N² 中间)不落显存 → 省带宽
PagedAttention (W4):分块 → KV(N×d 缓存)高效存储 → 省显存
flash 省"算出来的中间",paged 省"要存的中间"
```

### 1.6 三块拼图闭环(为什么 vLLM 快的完整答案骨架)

```
① 连续批处理(调度层)——批"活":随到随插、生成完即退
② PagedAttention(存储层)——批"装得下":同显存塞更大 batch
③ kernel 融合(算力层,flash-attn)——每步"算得快"
链条:省 KV 显存 → 更大 batch → decode AI≈batch(Day2)→ 吞吐近线性涨
```

## 五、面试题定稿:"PagedAttention 为什么省显存?"

**我的草稿(被批改)**:"利用了显存的物理碎片,按需存储,请求结束后立即释放。"
**问题**:①"利用碎片"表述反(是"不要求连续"→碎片空间也能用+不再产生新碎片);②漏**共享**;③漏**吞吐闭环**(面试官真正想听的)。

**定稿版(背这个)**:
> ①**消碎片**:传统给每请求预留一整块连续 max-len 显存——实际生成常远短于 max(内部碎片),释放后留洞塞不下新请求(外部碎片),利用率只有 60-80%。PagedAttention 把 KV 切成 16-token 的 block,逻辑页表映射任意物理块(像 OS 虚拟内存),两种碎片一起消,利用率近 100%。
> ②**按需**:生成到哪页给哪页,请求结束块立即回池。
> ③**共享**:相同前缀(system prompt/多轮/beam search)引用计数共享物理块。
> **闭环**:省下的显存 → 同卡塞更大 batch → decode AI≈batch → 吞吐近线性涨(我实测 batch=8 聚合 4.5×)。论文:吞吐 2-4× Orca、23× HF。

**配套一句话(串 W3)**:"我 W3 用 Triton 写过 flash-attention——分块省带宽;PagedAttention 是同一个分块思想用在 KV 存储上——分块省显存。"
