## 〇、三选手详细对照:串行 / 静态批 / 连续批 ⭐

### 0.1 三种调度方式是什么

| | 串行 | 静态批 | 连续批 |
|---|---|---|---|
| 调度单位 | 1 个请求 | 1 整批请求 | **1 个 decode step** |
| 典型实现 | HF 逐个 generate | HF batch + padding | vLLM LLMEngine |
| 权重复用 | 无(每请求重读 14GB) | 批内摊薄 | 批内摊薄 + 动态增减 |
| 新请求 | 立即独占 | 等整批结束(队头阻塞) | 下个 step 插入 |

**核心矛盾**:LLM 生成长度不可预测。串行浪费"请求间"的复用机会;静态批浪费"批内"的尾部;连续批把调度粒度压到单步,两边都不浪费。

### 0.2 三条时间线(8 请求,长度 30→170)

```
串行(HF,墙钟 20.87s):
req0(30)   |██|→0.6s
req1(50)         |███|→+1.0s
...每请求独占 GPU,一个接一个;总墙钟 = 各请求耗时之和
└── 早的请求几分钟前就完了,后面的只能干等(吞吐 38.3 tok/s)

静态批(HF,墙钟 4.59s,一次 170 步):
req0(30)  |██████░░░░░░░░░░░░░░░░░░░░░░░░░░|←30 步完,陪跑 140 步
req7(170) |████████████████████████████████|←170 步才算完
           └──────── 4.59s 全部一起返回 ────────┘
短请求被长请求拖死;批没结束前新请求只能排队(吞吐 174,但延迟烂)

连续批(vLLM,墙钟 3.82s):
req0(30) |██████→0.99s 返回(不等任何人)
req1(50) |██████████→1.40s
...
req7(170)|████████████████████████████████████|→3.80s
每步全批一起推进;谁完谁走;新请求随时插入(吞吐 209.7 且延迟各自最短)
```

### 0.3 十维对照表

| 维度 | 串行 | 静态批 | 连续批 |
|---|---|---|---|
| 墙钟(8 请求) | 20.87s | 4.59s | 3.82s |
| 聚合吞吐 | 38.3 tok/s | 174 tok/s | 209.7 tok/s |
| 30tok 请求何时回 | 第 1 个(但总墙钟最大) | 4.59s(陪跑 140 步) | **0.99s** |
| 最长请求 170tok | ~3.6s | 4.59s | 3.80s |
| 短请求延迟 | 看排位 | 被最长的拖 | 自己长度×步时 |
| 新请求等待 | 立即(独占) | 等整批结束 | 下个 step 插入 |
| GPU 空转 | 请求间隙 | 批间隙 | 几乎无 |
| 手动组批/padding | 不需要 | **需要(left padding)** | 不需要 |
| 流式支持 | 难 | 难 | **原生 SSE** |
| 适用场景 | 调试/单请求 | 长度齐、无实时性 | 生产/混合长度/流式 |

**后端桥**:串行 ≈ 同步 `for` 一个用户一个用户服务;静态批 ≈ "攒一批再一起跑"(攒批窗口=延迟);连续批 ≈ **线程池 `submit` 随到随跑 + 完成即回收**——你后端经验里最熟的那种动态调度,vLLM 把它做到了 decode step 粒度。

## 一、"为什么是 2×7B FLOP?"——2P 规则完整拆解 ⭐

### 1.1 2P 规则:每 token 前向 ≈ 2 × 参数量

**单 token 前向 = 一串线性层(矩阵乘)+ attention + 归一化。FLOP 大头全在矩阵乘:**

```
一个线性层 W(d_in→d_out) 处理 1 个 token(矩阵-向量乘):
  out[i] = Σ_j W[i][j] × x[j]
  对 W 的每个元素:1 次乘 + 1 次加 = 2 FLOP
  → 该层 FLOP = 2 × d_in × d_out = 2 × numel(W)

7B 模型所有线性层(numel 之和 = P,embedding 与 LM head 共享算一次):
  总 FLOP = Σ 2×numel(W) = 2P = 2 × 7×10⁹ = 14 GFLOP/token
```

**这就是"前向 ≈ 2P"的来源**——不是约等于,是"每个参数每 token 恰好一次乘加"的加总。它是 LLM 界放之四海的规则(Chinchilla 等 scaling law 都用它)。

### 1.2 你问的"attention 不是还有别的吗?"——对,但占比可忽略

```
attention 每 token 的额外 FLOP = 4 × seq_len × head_dim × num_heads × num_layers
  (QK^T、PV 各 2×seq×head×head_num,softmax 是 exp 更便宜)
7B, seq=1000:4×1000×128×28×28 ≈ 0.4 GFLOP
  2P = 14 GFLOP → attention 占比 ≈ 3%
seq=4096 超长:≈ 1.6G → 11%
```

**结论**:短序列下 attention 相对 2P 可忽略,所以 2P 规则成立;seq 上万时 attention 才值得单独算。这也是为什么"长上下文"是 attention 优化的主场(W3 Day6 的 Flash-Attention)。

### 1.3 参数的奇妙抵消:decode AI ≈ batch

```
decode 一步(整批 batch 个 token 各生成 1 个):
  总 FLOP = batch × 2P
  权重读  = P 参数 × 2B = 14GB(整批共享,只读一遍!)
  AI = (batch × 2P) ÷ (P × 2B) = batch × (2P/2P) = batch   ← P 消掉了!

decode AI ≈ batch(FLOP/B)
```

**推论一(单卡 decode 永远带宽 bound)**:
```
decode 吞吐上限 = 带宽 ÷ 权重字节 × batch = 936GB/s ÷ 14GB × batch = 66.9 × batch tok/s
  batch=1 → ~67 tok/s(实测 46.7,效率 70%)
  batch=8 → ~535 tok/s 上限(实测 209.7 = 平均批 4.7 × 66.9 × 0.7 ≈ 220 ✓)
3090 平衡点 38 → batch 得 >38 才 compute-bound,24GB 卡根本塞不下
→ 单卡 decode 的终局拼的是:批大小 + KV 显存管理(Day3 PagedAttention 存在的理由)
```

**推论二(decode vs prefill 不对称)**:
```
prefill(整 prompt 一次):FLOP = 2P×L,权重读一次 → AI = L
  L=1000 → AI≈1000 >> 38 → compute-bound
decode(逐 token):AI = batch → 永远 <38 → memory-bound
→ "输入越长越吃算力(prefill),生成越吃带宽(decode)"——这就是为什么有 chunked prefill。
```

**顺带(训练侧)**:前向 2P + 反向 ~4P → **训练每 token ≈ 6P FLOP**(Chinchilla 的 6ND 估计)。同一个 2P 规则,推理训练通用。

## 二、代码精读

### 2.1 `vllm_concurrent.py` 关键点

| 行 | 知识点 |
|---|---|
| `ThreadPoolExecutor(max_workers=8)` | 客户端并发;vLLM 服务端调度与客户端无关 |
| `temperature: 0.0` | 贪心解码、可复现——压测纪律:先固定随机性再谈数字 |
| `max_tokens` 30~170 异构 | 制造"生成长度异构",逼出连续批交错证据 |
| 按 `dt` 排序打印 | 完成时间表本身就是指纹:等差 = 每步全批齐推 |

### 2.2 `hf_batch.py` 关键点

| 行 | 知识点 |
|---|---|
| `tok.padding_side = "left"` | ⭐ decoder-only 批量生成的坑:右 padding 把 pad 塞进"未来位置",位置编码错乱;左 padding 让真 token 靠右、pad 被 attention_mask 屏蔽 |
| `torch_dtype=torch.bfloat16` | 和 vLLM 同 dtype,对照公平(Day1 教训) |
| `generate(**enc, max_new_tokens=170)` | ⭐ 静态批只能按最长的算:短序列撞 EOS 后空槽位继续陪跑到第 170 步 |

### 2.3 map vs submit 详解(线程池的两个提交姿势)⭐

代码里 [A] 用了 `ex.map`、[B] 用了 `ex.submit`——这是两个不同的"提交 + 取回"语义:

```
map:  一次提交一整个 iterable,按输入顺序取回
  res = list(ex.map(chat, range(8)))
  # res[0] 对应 chat(0),res[1] 对应 chat(1)... 顺序 = 输入顺序,不是完成顺序!
  # 内部机制:submit 全部任务,然后按序阻塞等待每个结果
  # 即使第 5 个任务先完成,也要等第 0 个的结果先出来

submit:提交单个,立即拿 Future(不阻塞),想什么时候取都行
  f = ex.submit(chat, i, 100, delay=1.5*i)   # 立刻返回 Future
  val = f.result()                            # 阻塞等这一个
  futures = [ex.submit(chat, i) for i in range(8)]
  vals = [f.result() for f in futures]        # 仍按提交顺序阻塞收
  # 想按"完成顺序"处理:用 as_completed(futures) —— 先完成的先 yield
```

| | map | submit |
|---|---|---|
| 提交 | 一整批 | 单个 |
| 返回 | 结果迭代器(按输入顺序) | Future 对象 |
| 阻塞语义 | 取第 i 个结果 = 等第 i 个任务 | `f.result()` = 等这一个 |
| 完成顺序 | 不可见(按序收) | 可见(`as_completed`) |
| 后端类比 | `asyncio.gather`(按 await 顺序) | 发请求拿句柄、事件驱动处理 |

**为什么 [A] 用 map、[B] 用 submit**:
- [A] 齐发:8 个请求**同时**发出(无 delay),只要"全部完成 + 按长度对应"——map 一行搞定,天然按 LENS 对齐;
- [B] 错峰:每个请求 delay 不同(0/1.5/3/4.5s),语义是"各自独立到达"——submit + `Future.result()` 逐个等更贴合。

**注意**:这是**压测客户端的工具**,和 vLLM 服务端调度**无关**——别把 map/submit 和连续批混为一谈(下面 Q4 就是栽在这)。

### 3.1 [A] 完成时间表 = 连续批指纹

```
req  0(30)  1(50)  2(70)  3(90)  4(110) 5(130) 6(150) 7(170)
```

### Q4 详细修正:问的是"服务端",答的是"客户端" ⭐

**原问题**:[B] 错峰实验,服务端日志的 `Running:` 会怎么变化?静态批下第 4 个请求要等多久?

**我的答案(错)**:描述了 client 会 `submit` 先发请求、各自 sleep、完成就返回;静态批要等 `2.05×3+1.5×(1+2)s`。

**错在哪**:
1. **答的是"客户端怎么发"(工具),不是"服务端观察到什么"(现象)**——问的是调度器的日志,我答的是压测脚本的机制;
2. 静态批时间的推算也乱了,没有说清"等多久"。

**正确解答**:
```
服务端日志长这样(vLLM 每 ~10s 打一行):
  metrics.py:467] ... Running: N reqs, Swapped: 0, Pending: 0, GPU KV cache usage: x%

[B] 错峰 4 请求 0/1.5/3/4.5s 到达,连续批下的观测预期:
  ① Running: 0 → 1 → 2 → 3 → 4(每来一个 +1,全保持 Running)
  ② Pending: 恒为 0 ← 关键!没有请求排队,到达即被调度进批
     因为连续批的调度单位是 decode step,每步都可以收新请求
  ③ 证据:4 个请求 dt 全 ~2.05s(平直)——若串行,延迟会随到达排位递增
     2.05→2.6→3.15→3.7,Running 长时间 =1,请求出现在 Pending

静态批对照:第 4 个请求 4.5s 到达时,前面 3 个的批可能还没跑完
  → 它进 Pending 排队 → 延迟 = 排队等待 + 自己 2.05s,明显 >2.05
  静态批 = "攒批窗口 + 整批串行",错峰到达下每个请求都在等
```

**一句话**:平直延迟 + `Pending=0` 就是连续批吸收错峰的可观测铁证;**以后被问到"服务端现象",盯服务端日志,别把客户端脚本当答案**。

## 六、坑合集(Day2)

1. **右 padding 会让 decoder 位置错乱**——批量生成必须 `padding_side="left"`。
2. **静态批必须按最长请求算**——短请求陪跑,结果也拿不到(4.6× 延迟差)。
3. **对照要同 dtype**(vLLM bf16 / HF 也要 bf16)。
4. **压测先固定温度/种子**,否则数字不可复现。
5. **vLLM vs 静态批 1.2× 是正常的**——连续批的账在延迟侧,别拿吞吐否定它。
6. **平均批大小**解释聚合吞吐和"8× 上限"的差——批不是全程满的。
7. **map vs submit 是客户端工具**,别和 vLLM 服务端调度混。
8. **答"服务端现象"题要看服务端日志**,别把客户端脚本机制当答案(Q4 教训)。
