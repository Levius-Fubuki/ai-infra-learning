## 〇、从 Day3 的结论到 Day4 的方向:AI≈B/4 罗盘 ⭐

Day3 算出 BLOCK=16 → **AI=4 → 带宽帽 3.74T**,实测 4.03 贴墙。调大 BLOCK 会发生什么?看**复用**:

```
DRAM 流量账(每个 A/B 元素从显存被读几次):
  A 读:M×K 元素 × (N/BN) 次      ← 每个 A 块被 N/BN 个 program 复用
  B 读:K×N 元素 × (M/BM) 次
  C 写:M×N × 1 次
  M=N=K、BM=BN=B 时:字节 ≈ 4 × 2N³/B,FLOP = 2N³(恒定!)
  → AI ≈ B/4(大 K 极限)

BLOCK 翻倍 → 重复读次数减半 → 有效 AI 翻倍 → 带宽帽翻倍:

| BLOCK(B) | AI≈B/4 | 带宽帽=936×AI | 实测(4096³) |
|---|---|---|---|
| 16  | 4    | 3.74T  | 4.03(Day3)✓ 贴墙 |
| 32  | 8    | 7.5T   | 9.03([5]) |
| 64  | 16   | 15T    | 16.11([5]) |
| 128 | 32   | 30T    | 18.21([5]) ← 收益递减 |

**注意最后两行的递减**:64→128 只 +13%,不是 +100%。因为 128 时撞上 shared 墙(99KB)、寄存器压力、波数跌近 1——**这就是 autotune 存在的意义:甜点不是"越大越好",是"涨不动之前那个点"**。

## 一、三个新机制

**1. autotune**:装饰器自动跑 configs 列表里每个组合、实测选最快。key=['M','N','K'] 按形状缓存;首次调用会打印 BENCHMARKING(本次没显示出来 → 手动 bench 替代,见 §四)。

```python
matmul_autotuned = triton.autotune(
    configs=[triton.Config({'BLOCK_M': 128, 'BLOCK_N': 64, 'BLOCK_K': 32,
                            'GROUP_M': 8}, num_stages=3, num_warps=4), ...],
    key=['M', 'N', 'K'],
)(matmul_kernel)          # 纯函数式包一层,原 kernel 仍可手动调(做实验靠它)
```

**2. group ordering**:相邻 program 处理**相邻** C 块,让 A/B 分块在 **L2(6 MiB)里被 GROUP_M=8 个相邻 program 复用**。无排序时 program 在整片 A 上乱跳,每块用完即走。

```
无排序:program 0,1,2,... 在整片 A 上乱跳 → L2 命中差
group 排序:先扫一条 GROUP_M×num_pid_n 的"带",再往下 → A 块留 L2 被复用
```

**3. num_stages(流水线)**:K 循环里把"下一次 load"和"本次 compute"重叠,DRAM 延迟被藏进计算。实测 §五——**对你 3090 的 64×64×64 几乎无效**,原因见下。

---

## 二、fp32 的墙:shared 内存 99 KB/block

```
shared/block 上限 ≈ 99 KB(3090 sm_86)
每个 stage 装 A+B 块:(BM×BK + BK×BN)×4 B
  128×128×64: (128×64 + 64×128)×4 = 64 KB/stage
    ns=2 → 128 KB > 99 KB → 装不下!
```

所以 fp32 下 **128×128×64 只配 ns=1**(不流水)。这也是 Day5 fp16 的动机之二:数据减半,同样的墙能装 2 倍 stage,大 BLOCK + 高流水同时成立。

## 三、代码逐行精读

### 变量字典(最优 config 128×64×32 为例)

| 变量/表达式 | 是什么 | 值/含义 |
|---|---|---|
| `pid_m`/`pid_n` | 行块/列块编号 | group ordering 拆出(§一.2) |
| `offs_m`/`offs_n` | C tile 行列坐标 | 128 / 64 个 |
| `offs_k` | K 游标 | 0..31,每圈 +=32 |
| `a_ptrs`/`b_ptrs` | A/B 分块地址矩阵 | (128,32)/(32,64) 广播寻址 |
| `k_mask` | K 轴越界保护 | `offs_k < K - k*BK`(Day3 教训) |
| `acc` | 累加器 (128,64) fp32 | tl.dot 乘加一体累积 |
| `num_warps`/`num_stages` | 调度参数 | 4 / 3(最优) |

### group ordering 具体拆解(grid=32×64=2048 program)

```
num_pid_in_group = GROUP_M × num_pid_n = 8 × 64 = 512
pid=1000:group_id = 1000//512 = 1,组内偏移 = 1000%512 = 488
  first_pid_m = 1×8 = 8
  pid_m = 8 + 488%8 = 8+0 = 8;pid_n = 488//8 = 61
  → 处理 C 的行块 8(行 1024..1151)× 列块 61(列 3904..3967)
```

### 一个具体的输出怎么算出来

```
program(pid_m=8, pid_n=61) 算 C[1024..1151, 3904..3967] 这个 128×64 tile
K 循环 4096/32 = 128 圈;第 3 圈(k 负责 64..95):
  a = A[1024..1151, 64..95]  (128×32)
  b = B[64..95, 3904..3967]   (32×64)
  acc += tl.dot(a, b, acc)
最终 C[1024, 3904] = Σ_{k=0}^{4095} A[1024,k]·B[k,3904],128 圈拼接,无越界
```

## 四、手动 benchmark 定案:平顶平台 + 最优 config ⭐

(autotune 缓存表显示不出 → 手写 `bench_configs.py` 逐个测,IEEE 全精度)

| Config | 分块 | ns | nw | ms | TFLOPS |
|---|---|---|---|---|---|
| 0 | 64×64×32 | 2 | 4 | 7.009 | 19.61 |
| 1 | 64×64×32 | 4 | 4 | 7.371 | 18.65 |
| 2 | 64×64×64 | 2 | 8 | 8.562 | **16.05** ← 最差 |
| 3 | 128×128×32 | 2 | 8 | 7.265 | 18.92 |
| 4 | 128×128×32 | 3 | 8 | 7.032 | 19.54 |
| **5** | **128×64×32** | **3** | **4** | **6.903** | **19.91** 🏆 |
| 6 | 64×128×32 | 3 | 4 | 7.078 | 19.42 |
| 7 | 128×128×64 | 1 | 8 | 7.309 | 18.80 |
| — | cuBLAS | — | — | 5.913 | **23.24** |

**三个结论**:

1. **平顶平台**:除 config 2 外全部 18.65~19.91,最优与次优差 2%。真正拉开差距的只有 config 2——所以**别在平台内纠结,找到平台就够了**。
2. **BK=32 完胜 BK=64**(config 2 垫底):BK=64 每 stage 的 shared 更重、流水更浅,3090 上不如 BK=32 多圈浅流水。
3. **nw=4 胜 nw=8 + 矩形胜方形**:config 5(128×64 nw=4)赢过 config 4(128×128 nw=8)——小块 → 每 SM 驻留更多 block → 延迟隐藏更好。**意外点**:按 DRAM 流量模型,128×128(1/BM+1/BN = 2/128)的流量比 128×64(1/64+1/128 = 3/128)**更少**,本该更快,实测却相反 → **流量模型不完整,寄存器/占用率/流水会反超**。对模型保持谦逊。

## 五、三大发现(全部实测背书)

### 发现 1:num_stages 几乎无效——占用率已替你藏延迟 ⭐(当日 Q3)

```
64×64×64:grid = 64×64 = 4096 program × nw=8 → 32768 warp ÷ 3936 ≈ 8.3 波
实测:ns=1 → 15.35,ns=2 → 15.99,ns=3 → 15.80(差 ~4%)

你想象的:program 等 load → 白等 → 流水线有用
实际:    program A 等 load → SM 切去算 B,C,D... → 没人白等 → 流水线多余
```

结论:**流水线在"大 BLOCK、少 program、低占用率"时才值钱**。Day5 换 fp16 大分块后它会开始有用。

### 发现 2:shared 墙是软的——编译器静默降级 ⭐(当日 Q5)

128×128×64 ns=2 需要 128KB > 99KB,预测"失败"。实测**没报错、跑出 19.59**——Triton 悄悄把 stages 降到能装下的深度。**"你请求的配置 ≠ 实际运行的配置"**,和 Day1"标签会撒谎"同族:脚本不报错 ≠ 它按你想象的方式跑。调参要常问:我请求的,真的是它跑的吗?

### 发现 3:大 BLOCK 变快的因果链(当日 Q2 纠正)

```
✗ "更少的 program 所以快"(相关性:总 FLOP 恒定,少 program 不会自己变快)
✓ BLOCK 变大 → 每个 A/B 元素重读次数↓(复用↑) → DRAM 流量↓ → (memory-bound)时间↓ → TFLOPS↑
   DRAM ≈ 4×2N³/B:BLOCK=32 → 17GB → ~18ms(实测 15.2);64 → 8.6GB → ~9.2ms(8.5);128 → 4.3GB → ~4.6ms(7.5,L2/占用率开始介入)
```

**"更少 program"是复用变好的副产物,不是原因**。区分相关与因果,是法医式性能分析的入门功。

## 八、坑合集(Day4)

1. **平顶平台内别纠结**:<5% 的差异是噪声,最优 vs 次优没意义;真台阶只有大分块/BK/ns 的切换。
2. **BK 不是越大越好**:64×64×64 是 8 个 config 里最差的(16.05),BK=32 全胜。
3. **shared 墙是软的**:超限不报错,静默降级——请求的 config ≠ 实际跑的。
4. **num_stages ≠ 一定快**:高占用率时流水线无活可干(Day5 大分块后才值钱)。
5. **对照 cuBLAS 用同一次运行实测**,别拿别处报的峰值硬比(22.39↔23.24 抖动)。
6. **autotune 缓存表显示不出时,手动 bench 是可靠替代**(今天的做法,还多得了平台全貌)。
7. **矩形 tile 能赢方形**:128×64 > 128×128,DRAM 流量模型算方形更优——对模型保持谦逊。
8. 大 BLOCK 的因果是**少搬字节**不是"更少 program"。
