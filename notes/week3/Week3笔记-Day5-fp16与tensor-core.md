## 〇、为什么是 fp16:双帽一起翻倍 ⭐(Q1 展开)

3090 的峰值阶梯(Week2 Day6 Roofline 的两个帽):

| 数据类型 | 算力帽 | 相对 fp32 |
|---|---|---|
| FP32 CUDA core | 35.6 TFLOPS | 1× |
| TF32 tensor | 71 TFLOPS | 2×(Day3 的 tl.dot 默认) |
| **FP16 tensor** | **142 TFLOPS** | **4×** |

但算力帽抬 4× 没用,除非 AI 也抬——否则还是带宽帽先顶。fp16 **同时抬两个帽**:

```
① 算力帽:fp16 tensor 142T
② AI 翻倍:输入 2 字节 → AI ≈ B/2(vs fp32 的 B/4) → 带宽帽翻倍

| BLOCK | fp32 AI | fp16 AI | fp16 带宽帽=936×AI |
|---|---|---|---|
| 64  | 16  | 32 | 30T |
| 128 | 32  | 64 | 60T |
```

**这就是 Week2 Day6"tensor core 是抬帽乘数"的完整兑现**:换 fp16 不是自动快,而是把两个帽一起抬高,才给快腾出空间。要凑近 142 还得让 AI 更高(更大分块/更少 DRAM 流量),但那是收益递减区(Day4 的 shared 墙/寄存器墙)。

**顺带**:fp16 尾数 10 位 ≈ TF32 的 10 位显式尾数,**精度量级相当**,但 fp16 吞吐 2×、还省一半带宽——matmul 里 fp16 全面优于 TF32。这也是 vLLM/训练真跑 fp16/bf16 的原因。

## 一、fp16 让昨天的"不可能"变"可能"

Day4 亲手测过:128×128×64 配 ns=2 要 128KB > 99KB,**fp32 下不成立**。fp16 减半字节:

```
128×128×64 fp16:stage = (128×64 + 64×128)×2 = 32 KB
  ns=2 → 64KB ✓   ns=3 → 96KB ✓(贴墙)   ns=4 → 128KB ✗(静默降级或"恰好成功",见 §四)
```

同样的墙,能装的 stage 翻倍 → 大分块 + 深流水同时成立。而**大分块 → 低占用率 → 流水线复活**(§四的 [3] 实测),Day4 发现 3 被闭环验证。

## 二、精度账:尾数 10 位 → 相对 ~3e-4(Q4 展开)

```
fp16:1 符号 + 5 指数 + 10 位尾数 → 单位舍入 2⁻¹¹ ≈ 4.9e-4
输入舍入:a→fp16、b→fp16,每个 ~5e-4 相对误差
乘积误差 ~1e-3;K=4096 随机符号,部分抵消 → 绝对误差 ~ sqrt(K)·1e-3·0.8 ≈ 0.05
结果量级 ~ sqrt(4096) = 64 → 相对误差 ~8e-4(实测 2.9e-4,同量级)

关键防线:累加器 acc 保持 fp32!
  若 acc 也 fp16:每加一步又舍入 → 误差随 K 线性增长(~K 倍,灾难)
  acc fp32:舍入只发生在输入,累积误差基本不涨
```

**所以验证门的 rtol 该给 1e-2 量级,且必须把"实现正确性"和"精度预算"分开**(§五)。

## 三、代码逐行精读

### 与 Day4 的三处不同

| Day4(fp32) | Day5(fp16) | 为什么 |
|---|---|---|
| `a = a`(fp32) | 调用侧 `a.half()` | 输入转 fp16,tensor core 入场券 |
| `tl.dot(a, b, acc, allow_tf32=...)` | `tl.dot(a, b, acc)` | fp16 输入自动走真 fp16 tensor core,无需开关 |
| 验证门 `atol=1e-4` | `atol=1e-2`(仍不对,§五) | 精度预算不同,验收要匹配 |

### 变量字典(128×128×64, ns=3 为例)

| 变量/表达式 | 是什么 | 值/含义 |
|---|---|---|
| `a`/`b` | fp16 输入块 | (128,64)/(64,128),2 字节/元素 |
| `acc` | **fp32 累加器** | tl.zeros((128,128), fp32)—— 精度防线 |
| `out` | fp32 输出 | tl.store 写 fp32,不降精度 |
| grid | program 数 | 32×32 = 1024 → nw8 = 2.1 波 |

### 一个具体的输出怎么算出来

```
program(pid_m, pid_n) 算 C 的 128×128 tile;K 循环 4096/64 = 64 圈
第 3 圈(k 负责 128..191):
  a = A[...] fp16、b = B[...] fp16,各 16KB
  acc += tl.dot(a, b, acc)   ← fp16 tensor core MMA,结果进 fp32 累加器
最终 C[i,j] = Σ_k a_ik·b_kj,64 圈,无越界(K-mask 在)
```

## 四、实测与复盘:72 为什么不是 142,ns 为什么活了

### 4.1 成绩单(4096³)

| 实现 | ms | TFLOPS | 备注 |
|---|---|---|---|
| **Triton fp16 autotune** | 1.908 | **72.04** | fp16 峰 142 的 51% |
| cuBLAS fp16 | 2.046 | 67.17 | 被反超 7% |
| cuBLAS fp32 | 5.756 | 23.88 | |
| D4 fp32 autotune | 6.813 | 19.91 | = 它自己的带宽帽 20,死贴 |
| Week2 k5 | — | 8.57 | 被反超 8.4× |
| naive | — | 0.51 | 一周 141× |

### 4.2 为什么 72 不是 142:还是带宽帽

```
best config(≈128×128×64):AI = 2N³/[2×(N³/BN + N³/BM)] = 64
带宽帽 = 936 × 64 = 60T
实测 72 > 60 → L2 复用把实际 DRAM 流量压到模型之下
```

两个对照印证:fp32 D4 的 19.91 **恰好等于**它自己的带宽帽(128×64 → AI≈21 → cap 20),死贴。**fp16 把两个帽都抬了,但瓶颈还是 DRAM 那个帽,算力帽 142 还有富余**——这是"compute-bound 的 kernel 用 tensor core"之前的中间态。

### 4.3 ns 扫描:流水线复活——机制不是"波数"(own it #5 修正)⭐

```
[3] 128×128×64 扫 ns:
  ns=1: 55.60 → ns=2: 64.05 → ns=3: 72.92 → ns=4: 75.01  (+35%)
对照 Day4 64×64×64:ns=1→3 只有 +4%
```

**❌ 最初解释(错,用户戳穿)**:128×128 大块"2.1 波低占用率"→ 流水线有活可干;Day4"8.3 波"→ 死。错在:两个 kernel 都被 shared 卡到**同样的 24 warp/SM**——64×64×64 fp32 与 128×128×64 fp16 每 stage 都是 32KB(99/32≈3 program × 8 warp),占用率根本没差;"2.1/8.3 波"是拿 48 warp 假想上限当分母编的伪代理,只反映总工作时长、不反映并发驻留。

**✓ 修正机制(两条)**:
```
① 每 stage 计算/搬运比:
   64×64×64 fp32:  每 32KB 跟 2×64×64×64 ≈ 0.52 MFLOP
   128×128×64 fp16:每 32KB 跟 2×128×128×64 ≈ 2.10 MFLOP  ← 4×
   流水线 = "把下一块 load 藏进当前块计算";搬运相同而计算多 4×,
   藏得进去的量就多 4×(fp16 减半字节,比例再拉开)
② 是否已贴带宽帽:
   Day4 ns1 实测 15.35 ≈ 自己的带宽帽(64×64×64→AI=16→cap≈15T) → 已饱和
      → 加深 ns 只多发 load 排到瓶颈后面 → 死(+4%)
   Day5 ns1 实测 55.6 < 自己的带宽帽(128×128×64→AI=64→cap≈60T) → 未饱和
      → 加深 ns → 内存级并行度↑(更多 outstanding load) → 喂满 DRAM → 活(+35%)
      ns3/ns4(72.9/75.0)超名义 cap 60 = L2 复用使实际 DRAM 流量低于模型
```

**沉淀(修正版)**:ns 收益取决于 **①每 stage 计算/搬运比(大块+小 dtype → 高)②带宽是否未饱和**。"program 少"只是"算得多"的伴生,不是原因(因果倒置)。波数要当占用率代理,必须先按 shared/寄存器受限算**实际驻留**(24 warp),不是 48 warp 假想——只有程序多到真住满 SM 时,调度旋钮才死。

**附:ns=4(要 128KB > 99KB)又"恰好成功"且最快**——soft wall 第三次出现(128×128×64 fp32 ns2 → 128×128×64 fp16 ns4),编译器静默调整,请求 config ≠ 实际 config 的又一记。

## 五、验证门修正案:own it ⭐(本篇最值钱的教训)

### 5.1 案发

```
[1] 验证门(fp16 vs fp32 参考,atol=1e-2, rtol=1e-2):
  256³: FAIL  max|err|=2.12e-02   相对误差 ≈ 3.0e-04
  4096³: FAIL  max|err|=1.01e-01  相对误差 ≈ 2.9e-04
```

**相对误差只有 3e-4,比 fp16 名义精度(1e-3)还好**——kernel 是对的。FAIL 是因为我把 `atol=1e-2`(绝对容差)和 `rtol=1e-2` 一起用,而 `allclose` 的判定是 `|c-ref| ≤ atol + rtol×|ref|`:绝对值误差随结果量级涨(4096³ 到 0.1),但某些元素 |ref| 较小,atol 撑不住。

### 5.2 修正:两档标准,别混

```python
# [1b] 修正的验证门:实现正确性 vs 精度预算分开
for n in (256, 4096):
    a, b = torch.randn(n, n, device="cuda"), torch.randn(n, n, device="cuda")
    ah, bh = a.half(), b.half()
    c = matmul(ah, bh)
    ref16 = (ah @ bh).float()                      # cuBLAS fp16:同精度预算的独立实现
    ref32 = a @ b                                  # fp32 真值
    print(f"  {n}³: 实现正确性 = {(c-ref16).abs().max().item():.2e}(应<1e-3)"
          f"  精度预算 = {(c-ref32).abs().max().item():.2e}(固有~3e-4 相对)")
```

- **实现正确性**:Triton fp16 vs cuBLAS fp16——同一输入、同一精度预算,只差累积顺序 → 应 ~1e-4,过了就是 kernel 没错;
- **精度预算**:Triton fp16 vs fp32/fp64 真值——~3e-4 相对,**固有,不是 bug**,是"你选择了 fp16"的代价。

### 5.3 反思(own it 第三次)

本周我在验收标准上错过的三处:Day2 naive 流量 448→512、Day1 AI 2→0.083、今天 fp16 的 atol=1e-2。**法医精神第一个适用对象是自己**——先怀疑验收标准,再怀疑 kernel。

### 5.4 意外收获:参考实现也要审查——cuBLAS fp16 默认低精度累加 ⭐

修正后的 [1b] 用户自己改的 gate **仍然 FAIL**,但这次是**物证**:

```
Triton fp16 vs cuBLAS fp16 = 2.53e-2(256³),和 vs fp32 真值(2.05e-2)几乎一样大!
```

推理链:
```
若 cuBLAS 用 fp32 累加:两实现共享完全相同 fp16 输入舍入,只差累积顺序 → 应 ~1e-4
实测 ~2e-2 → cuBLAS fp16 有超出输入舍入的额外误差 = 它在 fp16 里累加!
```

**凶手**:`torch.backends.cuda.matmul.allow_fp16_reduced_precision_reduction` 默认 **True**——cuBLAS fp16 默认用 fp16 做 reduction(累加)。**它比我们 fp32 累加的 kernel 还糙**。修复一行:

```python
torch.backends.cuda.matmul.allow_fp16_reduced_precision_reduction = False
# 再测:c vs cuBLAS fp16 应掉到 ~1e-4(纯累积顺序差)→ 实现正确性 PASS
```

**两个新教训**:
1. **"实现正确性"的参考实现也要审查**——NVIDIA 默认也是低精度累加,和 Day3 的 `allow_tf32` 是同一族"隐蔽默认项";
2. **fp16 误差结构:绝对误差几乎恒定**(由输入舍入累积决定,~0.05@4096,与结果量级无关)→ 小量级元素"相对误差"巨大 → `allclose` 的逐元素 `atol+rtol` 判据不匹配,**应该用全局相对判据 `rel = max|err| / max|ref|`(~3e-4)**,或 `atol` 取误差地板量级。

### 5.5 结案:flag 预测翻车,真凶是"输出舍入"——验证门三层收官 ⭐

§5.4 末尾那个预测(**关掉 accumulation flag 后 c vs cuBLAS fp16 应掉到 ~1e-4**)实测**没有兑现**——own it 第 4 次。数字把它钉死了:

```
预测:关 allow_fp16_reduced_precision_reduction → 差距应掉到 ~1e-4(纯累积顺序差)
实测:没掉,仍 ~2.7e-2 → 预测错
真凶:cuBLAS fp16 matmul 的**输出本身就是 fp16 张量**,大值元素被舍到半 ulp:
      max|ref| ≈ 64,舍入误差 ≈ 64 × 2⁻¹¹ ≈ 0.031 ≈ 实测 2.7e-2 ✓(数字指纹咬合)
终极实验:c.half() vs cuBLAS fp16 = **0.00e+00,比特级一致**
      → 两边内部计算完全相同,全部差距来自"我们输出 fp32、它输出 fp16"
```

**验证门三层收官**:
1. **实现正确性**:c vs 真值的 rel = 3e-4 ≈ fp16 输入舍入理论地板 → PASS;
2. **参考噪声**:c vs cuBLAS fp16 的 2.7e-2 是**参考自己**的输出舍入,不是我们的误差(预测归因于累加 flag = 错);
3. **终极证明**:比特级一致。

**终局结论**:我们的 kernel(fp32 acc + fp32 输出)**比 torch 默认 fp16 matmul 更精确,还快 7%**(72.04 vs 67.17)。这一条可以直接进面试:"我写的 Triton fp16 matmul 在 3090 上比特级对齐 cuBLAS,精度更高(fp32 输出),速度快 7%。"

## 六、精度阶梯([4] 实测)

```
256³,以 fp64 为真值:
  fp32 最大误差 = 1.54e-05
  fp16 最大误差 = 2.21e-02
```

fp16 只有 **3 位十进制有效数字**(2⁻¹¹≈1e-3)。这就是为什么生产里:
- **训练**:fp16/bf16 混合精度(关键 op 用 fp32 累加,就是 acc=fp32);

- **敏感场景**(某些科学计算):必须 fp32/fp64。

选 dtype 就是选"你愿意为速度放弃几位数字"。

### Q1:fp16 峰值是 fp32 的几倍?兑现 4× 最缺什么条件?

**我的答案**:"4 倍;shared_memory 的大小和极限 AI 的大小。"

**批改**:数字对。"条件"答到了两堵墙的名字,但没说清它们和 4× 之间的**因果链**——算半对。

**完整解答**:4× 是**算力帽**的倍数(35.6→142);但决定实测的是**先顶的那顶帽**。兑现路径:

```
fp16 同时抬两帽:算力 142T + AI≈B/2 → 带宽帽×2
要拿到 4×,必须让带宽帽 ≥ 142T:AI ≥ 142T ÷ 936GB/s ≈ 152 FLOP/B
按 AI≈B/2 反推 BLOCK≈300+ —— shared 墙(99KB)/寄存器墙根本到不了
实测 best config AI=64 → 带宽帽 60T 先顶,72 靠 L2 超帽 = 峰值的 51%
```

准确的说法:**shared 墙挡的是"继续抬 AI 的手段",而 4× 的直接条件是"带宽帽让位"(瓶颈切换到算力帽)**——两者是间接关系,不是同一个东西。面试里这个区分就是"懂 roofline"和"背过 roofline"的区别。

### Q2:预测 fp16 autotune 的 4096³ TFLOPS

**我的答案**:"至少大于 4×19.91"(即 ≥79.6)。

**批改**:方向对(会大涨),数值错——实测 72.04,只有 3.6×。

**错在哪**:把"帽翻 4×"直接乘在**上一次的实测值**上。但 19.91 不是 fp32 的算力峰——它恰好贴在 fp32 那个配置**自己的带宽帽**(≈20T)上。fp16 翻的帽是**峰值口径**的,不是"相对 19.91"的。

**正确预测路径**:
```
① 问:fp16 下 best config 的 AI?≈B/2 = 64 → 带宽帽 936×64 = 60T
② 加 L2 复用修正(实测常超帽 10~20%)→ 预测区间 55~75
③ 实测 72.04,落区间顶部 ✓
```

**教训(值得抄进任何性能预测)**:倍数要乘在"**限制它的那个量**"上,不能乘在"上一次的成绩"上——先问"上次被什么卡住",再问"那个量这次翻了多少"。

### Q3:为什么 fp16 能让 128×128×64 的 ns 从 1 升到 3?

**我的答案**:"(128×64+64×128)×2×3 == 96KB < 99KB"。

**批改**:✓ 满分,shared 算术一字不差——fp16 每元素 2 字节,stage = (BM×BK + BK×BN)×2 = 32KB,ns=3 共 96KB 恰好贴墙放下。这就是"fp16 让大分块+深流水同时成立"的定量版,也是 Day4 那堵 soft wall 的解除(ns=4 要 128KB 仍越墙,soft wall 第三击)。

### Q4:验证门 rtol 给多少?fp16 相对误差怎么算?

**我的答案**:"1e-2,但我不太清楚是怎么算的。"

**批改**:数值对,推导空缺——补全五步:

```
① 尾数 10 位 → 单位舍入 u = 2⁻¹¹ ≈ 4.9e-4
② a、b 各自舍入 → 每个乘积的相对误差 ~2u ≈ 1e-3
③ K=4096 项累加、符号随机 → 误差按 √K 抵消着走(随机游走),不按 K 走:
     绝对误差 ≈ √4096 × 1e-3 ≈ 0.06(实测 max|err| 0.05~0.10)
④ 结果量级 ~√K = 64(max|ref| ~250)→ 相对误差 ~1e-3 量级(实测 2.9e-4)
⑤ 关键防线 acc=fp32:舍入只发生在输入;若 acc 也 fp16,误差按 K 线性涨 ≈4096× = 灾难
```

**点睛**:**√K vs K = "随机游走" vs "单向累加"**,这一行就是混合精度训练(acc 用 fp32)的全部原理。rtol=1e-2 正是给"~1e-3 相对误差"留了 10× 安全余量。

### Q5:[3] 的 ns 扫描会是什么趋势?

**我的答案**:"ns 增加,TFLOPS 增加。"

**批改**:✓ 方向全对,且是五题里预测得最果断的——实测 55.6→64.0→72.9→75.0(**+35%**)。**但我当时给的机制解释是错的**(被用户一句"SM 只驻留 48 warp"戳穿,own it #5),已修正为 §4.3 版。

**❌ 我最初给的解释(错)**:128×128 大块"2.1 波低占用率"→ 流水线有活可干;Day4 64×64"8.3 波"→ 死。

**为什么错(一句话)**:两个 kernel 的并发驻留都是 **24 warp/SM**(shared 受限:每 stage 都是 32KB → 3 program×8 warp),占用率完全相同;"2.1/8.3 波"是拿 48 warp 假想上限当分母编的伪代理——它只反映总工作时长,不反映并发驻留。用不存在的占用率差解释 ns 差 = 因果倒置。

**✓ 修正机制(详见 §4.3)**:
```
① 每 stage 计算/搬运比:128×128×64 fp16 每 32KB 算 2.10 MFLOP
   vs 64×64×64 fp32 的 0.52 MFLOP(4×)→ 流水线能藏进 load 的计算多 4×
② 带宽余量:Day4 已贴自己带宽帽(15.35≈15T)无余量 → ns 死;
   Day5 未贴(55.6<60T)→ 加深 ns → 内存级并行度↑ → 喂满 DRAM → 活
```

**沉淀(修正版)**:**旋钮的死活由"每 stage 计算/搬运比 × 带宽余量"决定,不是占用率**。预测调度旋钮前,先算 per-stage 计算/搬运比,再查实测离带宽帽多远;要用波数当占用率代理,必须先按 shared/寄存器限制扣出**实际驻留**。**顺带把 48 warp 这个我偷懒用的数字纠正了**:sm_86 的 48 warp/SM 是硬件上限,不是实际驻留——一个被 shared 卡住的 kernel 根本住不满它。

## 九、坑合集(Day5)

1. **验证门必须"实现正确性"与"精度预算"分开**:对独立实现(cuBLAS fp16)测正确性,对真值报固有误差;别用 fp32 的 atol 套 fp16。
2. **fp16 累加器必须 fp32**:acc 若 fp16,误差随 K 线性增长(灾难);输入舍入才是 fp16 的主要代价,累积不涨。
3. **4× 峰值是理论**:带宽帽(60T)先顶,实测 72;想再上要抬 AI 或减 DRAM 流量,收益递减区。
4. **num_stages 死/活取决于"计算/搬运比 × 带宽余量"**(own it #5 修正):不是占用率/波数——64×64 与 128×128 驻留都是 24 warp/SM,差在每 stage 计算量 4× 和带宽饱和与否;"有时有用"是常态。
5. **soft wall 第三击**:ns=4(128KB>99KB)静默"成功"且最快——请求 config ≠ 实际 config,别按请求值推断。
6. **fp16 只有 3 位十进制**:和 fp32 比误差 1431×;选 dtype=选精度,匹配场景。
7. 计划里"fp16 峰 ~71"是错的:**71 是 TF32,fp16 tensor 是 142**——查资料以 NV 官网峰值表为准。
8. **参考实现也有精度边界**:cuBLAS fp16 的**输出本身就是 fp16**(大值元素舍入误差 ≈ max|ref|×2⁻¹¹ ≈ 0.03),拿它当正确性参考会把参考自己的噪声算到你头上;另有隐蔽默认项 `allow_fp16_reduced_precision_reduction=True`(fp16 累加,§5.4)。终极对照是**比特级**:`c.half()` vs cuBLAS = 0.00e+00(§5.5)。
9. **fp16 用全局相对判据**:`allclose` 的逐元素 atol+rtol 不匹配"绝对误差恒定"的结构;用 `rel = max|err|/max|ref|` 或 atol=误差地板量级。
